## Implementation status and deviations (Phase 0, as of 8 Nov 2026)
Implemented in `knowledge/rules.json`, each with one positive and one negative fixture: **A1–A4, B1–B19, C1–C3** (26 rules, 49 since 9 Nov, see "Addendum: source code research and security review"; B16–B19 from the Doctor knowledge base, see "Addendum: Doctor knowledge base"; A2, A4, C1–C3 since 8 Nov, see "Addendum: A2, A4, C1–C3").

Found when comparing with the current SM+ README (drakmor/ShadowMountPlus):
- **config.ini has sections** (`[scan] path=`, `[scan] depth`, `[general] debug`, `[fakelib] enabled`). The collector understands sections and the older flat keys (`scanpath`, `scan_depth`, `debug`, `backport_fakelib`). Defaults per README: depth 1, `debug` on. Whether `[fakelib] enabled` is on by default (B5) is not stated in the README – the assumption "on" comes from this file.
- **Default scan paths** are broader than originally noted (`…/homebrew` and `…/etaHEN/games` per drive, plus `/mnt/usb0..7`, `/mnt/ext0..1`).
- **`autotune.ini`**: According to the README, old autotune values move to `profiles.ini` (`[image:FILE] sector_size`). B15 stays `todo` until the format has been verified on the console.
- **B14** ("Register failed"): named in the README as a notification, not as a `debug.log` line → `todo`. *Superseded (8 Nov): The line format is verified against a real log, see "Addendum: Doctor knowledge base".*
- **B6/B7**: Images cannot be inspected without mounting them. The rules evaluate the state under `/mnt/shadowmnt/` (layout provisional, verify in Phase 2) → `todo`.
- **A1**: The firmware limit is not established. The source (kstuff-lite #94) only names FW 13.60; the rule therefore applies from `>=13.60`.
- **B3/B4**: Crashes or startup failures cannot be detected from a snapshot; the rules only check the reported combination of FW/version/config. Versions and origin of kstuff come provisionally from `components` in `system.json` (console source open).

## Fixes (Phase 1, as of 8 Nov 2026)
Implemented and tested (apply → undo = identical file tree): `rename_image_parentheses` (B2), `smp_set_key` (B3, B9, B10, B13), `smp_disable_conflicting_backpork` (B5), `move_duplicate_titleid` (B8), `fix_image_nesting_hint` (B6, B7; hint only).
Parameters are stored as `fix_params` in the rule (see `libmedic/include/medic/fixes.hpp`).

Open points to be clarified before use on the console:
- **B5**: Where BackPork is started is not documented. The fix comments out the entry in `/data/ps5_autoloader/autoload.txt` (path from a file list, syntax unchecked). If the file does not exist, the fix changes nothing and says so. The running BackPork process only ends with the restart.
- **B8**: Duplicate sources go to `<scanpath>/_duplicates/` (same drive, no copying). With `scan_depth >= 2`, SM+ might scan the folder too – the plan points this out. Whether SM+ skips folders starting with `_` is unchecked. *Superseded (9 Nov): SM+ only skips names with a `.` at the start; the fix now moves to `<scanpath>/.duplicates/`.*
- **B8, extension (10 Nov): folder and image of the same game.** On the test console, ShadowMount+ showed "Duplicate PPSA… ignored" at every start (game folder and `.exfat` image of the same title, the image has no TITLE_ID in its name). For this the collector reads `/user/app/<TITLE_ID>/mount_img.lnk` (path of the image) and `mount.lnk` (path of the folder) – SM+ creates both files for each installed title (read from real files on the console). The image thus gets its TITLE_ID, `smp.titles[]` carries `active` for the source that SM+ uses, and the fix keeps that source and moves the other to `.duplicates/`. Fixtures `d1_pos`, `d1_neg_image_only`, `d1_neg_other_title` (synthetic).
- **B9/B10**: The fix writes to the `[scan]` section, or stays with the flat format if the file has no sections.
- **Deletion**: Nothing is deleted. Only exception: on undo, folders that the fix itself created and that are empty are removed (e.g. `_duplicates/`).

## Addendum: comparison with the local SM+ README (1.7beta5 state)
Source: `README.md`, `config.ini.example` and the Payload Manager source code from the local folder `PS5 SDK usw`. From this follows:
- **Two config.ini formats** exist depending on the version: flat keys (this README) and sections (GitHub page, newer development). Collector and fix engine understand both.
- **B3**: `kstuff_game_auto_toggle` is `1` by default. The rule therefore also fires when the key is missing (fixture `b3_pos_default`).
- **B10**: `recursive_scan=1` forces `scan_depth=2` (fixture `b10_neg_recursive`). The folder `backports` does not count as a game source (fixture `b8_neg_backports`).
- **B6/B7**: Mount points `/mnt/shadowmnt/<image>_<hash>` and `/mnt/shadowmnt/pfsc/<image>_<hash>` are documented → status `doc`.
- **B15**: `image_sector=<file>:<size>` in `autotune.ini` is documented (SM+ writes it when the cluster size does not match the sector size) → `doc`.
- **B14** stays `todo`: "Register failed" is named in the README as a notification. *Superseded (8 Nov): The line format is verified against a real log, see "Addendum: Doctor knowledge base".*
- **B5 fix**: The autoload lists (`/data/ps5_autoloader/autoload.txt`, Payload Manager: `/data/pldmgr/autoload.txt`) do not know comments: `!<ms>` is a wait time, every other line is a file name. The fix **removes** the BackPork entry (original in the backup, `undo` restores it) instead of marking it with `#`. The path of the list depends on the autoloader; both are on the whitelist.

## Addendum: A2, A4, C1–C3 (8 Nov 2026)
The last five rules needed new facts. For this, the platform now knows process start times (`ProcInfo`), the console start (`boot_epoch`) and a port test (`local_port_state`); snapshots and export carry them (`procs.json` objects `{"name","start"}`, `system.json` `boot` and `ports`).

- **A2**: The source is weak. In the issue a community member advises waiting "a min or so", without a measured time and without a proven cause (DNS and cookies were changed at the same time). The rule is therefore only a hint (`info`, `community`). The ShadowMount+ log only has times of day (`[15:12:42]`), no uptime; so the rule calculates with process start times instead of log timestamps. On the test console: jailbreak chain 188 s after the start (kstuff first), the rule does not fire there.
- **A4**: The check is a connection to 127.0.0.1:9021 without data. Only "connection refused" counts as closed; a timeout (loader busy) stays unknown, in which case the fact is missing. In addition, neither `elfldr` nor `etaHEN` may be running (etaHEN brings its own loader). On the test console: port open. Status stays `todo`; the "closed" case has only been tested on the PC (fixtures).
- **C1**: The limit "older than 1.23" from the first research is **not substantiated**: 1.23 is the version from which the plugin updates itself. According to the release notes of 1.53, the error CE-105733-9 comes from "earlier test builds" of the icon feature that appeared with 1.53. 1.30 and 1.53 are published, so the rule reports versions **between 1.30 and 1.53** (the earlier versions 1.22 to 1.30 are presumably not affected because the icon feature only appeared with 1.53; this is a derivation). The error code itself cannot be detected from a snapshot. The version comes from the log (`ps5-theme 1.23 starting`; the format is derived from the plugin's strings, no real log was available) or hard-coded from the plugin file (checked against a real `ps5-theme.plugin` 1.23). On the test console ps5-theme is not installed. Status `todo`.
- **C2**: The source (release notes CD Player 1.1.2) only names the sizes (16 GiB instead of 256 MiB). That the reservation is stored in `param.json` as `downloadDataSize` (MiB) is a derivation: the values of the test console fit (256 for BFpilot and USB formatter, 64, 0). An oversized case could not be reproduced (CD Player is not installed). It is only reported if the reservation is ≥ 4096 MiB **and** the app's files together stay below 1 GiB; if the content is larger or cannot be determined reliably (over 20,000 entries), the rule stays silent. The snapshot export omits `/user/app` (it knows no file sizes), so no C2 finding can arise from an export; a test guards this. Status `todo`.
- **C3**: The 5 % threshold is our own heuristic without a source (reference to this repo, because the schema requires a URL). Only `/data` counts; full USB drives trigger nothing (fixture `c3_neg`).

## Addendum: B11 after a finding on the console (8 Nov 2026)
The rule counted `source not stable yet` in the whole log (at least 3 lines). On the test console this triggered a hint that was not one: every normal copy operation produces one or two such lines before ShadowMount+ installs the source (real log: one game two lines, then `Installing:`; our just-uploaded starter one). Three lines from **different** sources are normal operation. Now the collector counts per source (`smp.unstable_sources[]`, the key is the path in the line) and the rule fires from 3 lines of the same source. Fixtures: `b11_neg_distinct_sources` (the lines of the real log) and `b11_pos_named` (name and path with parentheses). The rule version is therefore `2026.11.09`; **with every change to the content of the rules, increment `db_version`**, otherwise the rule update rejects the file as "not newer". For the download afterwards run `make sign-rules` (see `docs/en/PHASE5.md`).

## Addendum: Doctor knowledge base reviewed (8 Nov 2026)
Reviewed was the `knowledge_base.json` of the PS5 Jailbreak Doctor (MIT, version 2026.10.17.1: 32 rules and 5 entries of a compatibility matrix). The Doctor evaluates **logs on the PC** by text pattern; PS5 Medic evaluates **facts** of the console. What was therefore adopted is whatever can be recognized from the ShadowMount+ log or a live fact, with our own texts. The sources were **checked individually on GitHub** (status, wording of the log lines, release notes); the Doctor state is from 17 Oct and partly outdated (e.g. issues 152 and 153 have since been closed).

**Adopted:** B16 (hook lost; issues 145/147), B17 (hook not installed; issue 109), B18 (image cache full; issue 32), B19 (API not responding; issue 152, **with a live port check instead of a log pattern**). B14 now also recognizes `[REG] FAIL: 0x…` (see below).

**Already covered:** Parentheses in the image name (B2), duplicate TITLE_ID (B8), "source not stable" (B11), scan path problems (B9/B10), 1.7beta3 crash with auto-toggle (B3), registration failed (B14), BackPork conflict (B5).

**Not adopted, with reason:**
- *Need klog or crash logs of the game, which PS5 Medic does not read:* PRX module errors, `param.json` missing/invalid, `libc.prx` missing, "crashed before kstuff pause", SIGSEGV/SIGBUS, kernel panic after loading kstuff, `/dev/klog` busy, "connection refused" (that is a PC message of the Doctor).
- *Events rather than state, cannot be detected from a snapshot:* kernel panic when moving USB→ext1 (issue 127), CE-105773-3 after quitting a folder game (128), CE-108262-9 (143), trophy registration 0x80551618 (97, the message appears on screen, a log line is not substantiated), FPKG not recognized after reset (140/149).
- *Too general, would also hit healthy logs:* "awaiting same-app handoff" (appears in the healthy log of the test console at every game end; issue 153 has also been fixed), general installation errors, "game does not start".
- *Source not findable:* "`/preinst/common/font`" (issue 132 returns 404; access was released anyway according to release 1.7beta5).
- *Not substantiated or not checkable:* file name length (limit unknown), mount with `Invalid Argument` (0x16; no log wording in the issue), 80F50005 as its own rule (one title, no known cause; the code is now in the evidence of B14).
- *Compatibility matrix:* Notes on 1.7beta2 + LZ4 + kstuff 1.11 and on 1.7beta5 ("etaHEN not with this build") describe individual cases or general release notes; the second is covered in the core by `hen.etahen_with_kstufflite_latest_fw`.

**B14 and language:** The `NOTIFY:` texts of SM+ follow the console language (`language=auto`; on the test console they are in German, e.g. "Duplikat … ignoriert"). The pattern `Register failed` would therefore never match on a German console. The line `[REG] FAIL: 0x…` is not translated; B14 recognizes both. Line format per issue 141: `[REG] FAIL: 0x80f50005` and `NOTIFY: Register failed: <name> (<TITLE_ID>)`. Healthy lines (`[REG] Installed NEW!`, `[REG] Skip (already present in app.db)`, `AppInstallAll bridge consumed: … result=0x00000000`) do not match (fixture `b16_neg`).

**B19 in detail:** At startup SM+ writes `[API] HTTP/JSON ready: http://0.0.0.0:10101/api/v1 …` (real log, 1.7beta11, test console). From this arise `smp.api.bind`, `smp.api.port` and, if the platform can check the port, `smp.api.state` (connection attempt to `127.0.0.1`). Without a ready line (API off, older version, startup not completed) there are no facts and no finding; when bound to a specific LAN address, a loopback attempt says nothing, and the state stays unknown. On the test console the port is open, there is no finding. The rule version is `2026.11.10`.

## Addendum: ShadowMount+ 1.7beta12, configuration format v2 (8 Nov 2026)
On 8 Nov, 1.7beta12 was released with a new configuration format (v2): `config.ini` with `[config] version = 2` and sections (`[general] debug`, `[scan] depth/path/interval_seconds/stability_wait_seconds`, `[fakelib] enabled`, `[api] bind_address/port`, …), values `on/off/true/false/yes/no/1/0`, plus `profiles.ini` for individual games and images (`[game:TITLE_ID]`, `[image:FILE] sector_size`). On first start SM+ converts the old files (`config.ini`, `autotune.ini`, `smb.json`; backup `config-v1-backup`); according to the release note, changes to `config.ini` take effect at runtime. The test console still runs 1.7beta11 (flat keys); *Superseded (9 Nov): The test console has been running 1.7beta12 since 9 Nov, the result is at the end of this section.*

What follows from this (checked against `src/sm_config_file.c` and the example files of 1.7beta12):
- The collectors already read both formats (section with `legacy_key` as a flat key, `on/off` as truth values). New: **values are read as SM+ does it**: `#` and `;` introduce a comment after the value (v1 and v2), in v2 a value may be in quotation marks (then `#`/`;` inside do not count, backslash escapes). Before, `path = "/mnt/usb0/Meine Spiele"` would have been read with the quotation marks as the scan path (wrong findings for B9/B10). Fixtures `b13_pos_v2`, `b13_neg_v2_defaults`, `b13_pos_v1_comment` and fact tests.
- The INI editor (fixes B3, B9, B10, B13) sets `depth=2` or `debug=1` in a v2 file at the end of the matching section and leaves comments and order in place; SM+ trims key and value, `1` is a valid truth value. Tests with a v2 file whose defaults are commented out (replaces an existing line including the comment after it).
- **B15** (`autotune.ini`, `image_sector`) can no longer fire under v2: `autotune.ini` is abandoned, automatic sector corrections are stored in `profiles.ini` (`[image:FILE] sector_size`), without being able to distinguish an automatic one from a manual one. Stays `todo`.
- **B3** (`kstuff_game_auto_toggle`) only applies to 1.7beta3; in v2 the key no longer exists (the old auto-pause was removed with 1.7beta5).
- The scan path rules continue to apply: "at least one `[scan] path` replaces the built-in paths" (B9); new is that `/mnt/shadowmnt` and `/mnt/shadowmnt/pfsc` are always added, which changes no finding.
### Confirmed on the console (9 Nov 2026, 1.7beta12, FW 12.00)
The check-up ran with a file converted by SM+ itself; in addition the snapshot on the PC (`medic-cli check`) and one copy each with a changed value.
- **Conversion:** On first start SM+ creates `config-v1-backup/` (log line `[CFG] configuration migrated to v2; originals saved in /data/shadowmount/config-v1-backup`) and writes a **slim** `config.ini` only with the previously set values (`[config] version = 2`, `[general]`, `[emulators]`, `[fakelib]`, `[library]`, `[api]`, `[fan]`, `[scan]`), without the comment template. The old line `fakelib_mode=<TITLE_ID>:disabled` is now in `profiles.ini` as `[game:<TITLE_ID>] fakelib = disabled`. New key names from practice: `[api] bind_address`, `[scan] depth`, `[fan] target_temperature = system`, `[library] remove_missing` / `remove_delay_seconds`, `[fakelib] default_mode`, `[emulators] update_enabled`. The backup contains the old `config.ini`, `autotune.ini`, `smb.json` as well as `ready.ini` and `profiles-v2.ini` (the latter two presumably handover files of the conversion, not checked further).

## Addendum: source code research and safety review (9 Nov 2026)
Four evaluations on 9 Nov: ShadowMount+ (source HEAD = 1.7beta12, issues since August), the rest of the jailbreak stack (Payload Manager 0.6.3, WebKit autoloader, elfldr, etaHEN, kstuff-lite, nanoDNS), PS5 system and memory errors (Sony support pages, SDK samples), and a review of the fix engine for safety and crash resistance. **Answers to the open points (from `sm_config_*.c`, `sm_scan_tree.c`, `sm_scanner.c` 1.7beta12):**
- **Flat v1 lines in a v2 file are not read.** Every line belongs to the most recently seen section; SM+ only accepts known pairs (section, key) and writes `[CFG] unknown setting` to the log for the rest. Another tool that appended `scan_depth=2` to the end of the file under v1 therefore has no effect under v2. For this reason the collector no longer counts such lines (depth, scan paths). New rule `smp.v1_keys_in_v2` together with fix `smp_translate_v1_keys`; the correspondences are verified against the conversion on the test console (old `config-v1-backup/config.ini` against the new one).
- **Runtime reload:** SM+ watches `config.ini` and `profiles.ini` via kqueue (250 ms debounce). API, scan paths, depth, interval, language, debug and quiet take effect live; `profiles.ini` only at the next mount, the fan target at game start. Log lines: `[CFG] loaded: …`, then `[CFG] runtime config reloaded` or `… reload failed`. No key that requires a restart was found.
- **An invalid value discards the entire configuration** (1.7beta12; under beta11 it was merely skipped). At startup the payload terminates, and the message appears only on the console; on a reload the old state stays. The new rule `smp.config_rejected` checks the file against SM+ rules (boolean values, depth 1–2, interval 1–3600, wait times, fan target `system` or 50–91, lines without `=`, `version` ≠ 2) and evaluates `[CFG] invalid/cannot read` in the log.
- **Scanner:** Names starting with `.` are skipped at every level, `_` is not. Consequence: `_duplicates` was also scanned at `scan_depth=2`, so the moved duplicates would have come back. **The fix `move_duplicate_titleid` now moves to `<scan path>/.duplicates/`**, and the collector mirrors the scanner's rule (skip dot names, not `_…`). This settles the open point "B8: whether SM+ skips `_` folders".
- **Autotune (B15):** under v2, SM+ writes `[image:<file>] sector_size` to `profiles.ini` and logs the language-neutral `[CFG] image sector autotuned: <file>=<N>`; B15 now recognizes both.

## Addendum: safety review of the fix engine (9 Nov 2026)
A reviewer read the fix engine and the rule download (findings checked individually against the code). No bypass of confirmation or signature; weaknesses in crash/power-loss consistency, undo and whitelist, now fixed and tested (`recovery_tests`, `stack_tests` in `tests/test_fixes.cpp`):
- **Aborted transactions** (power loss, USB unplugged) could not be recovered: every operation is now written to the journal as an `intent` **before** execution, with backup path, hashes, folders to be created and the allowed roots. For each operation, `undo_txn` determines whether it is in the "after" state (roll back), the "before" state (already done) or foreign (abort, touch nothing). It therefore also works for transactions in the `incomplete` state and can be repeated after a half-failed undo; the UI offers Undo for this. A rollback that itself fails results in `incomplete` instead of `aborted`.
- **fsync and atomic writing:** `PosixRw` writes via a temp file (`O_EXCL|O_NOFOLLOW`, removed beforehand), `fsync` for file and folder, then rename. The **journal is append-only** (`append_file`, `O_APPEND`, `fsync`) instead of being rewritten completely each time. Unreadable journal lines (remnant of an aborted write) are skipped; the commit entry states the number of operations, `undo_txn` refuses if fewer entries are readable.
- **Stale plan:** write changes remember the SHA-256 of the original file; if the file has changed since the preview (SM+, FTP, user), `apply_plan` refuses instead of writing a different diff than the one shown.
- **Whitelist:** additional roots from scan paths only under `/data/…`, `/mnt/usb<N>` and `/mnt/ext<N>` (before, also `/user/app`, `/system_data`, `/mnt/sandbox` …). The roots are recorded in the journal, `undo` uses them in addition to today's; nothing is ever written or cleaned up for a path in the journal without a whitelist check (the backup path must be under `/data/ps5medic/backups`).
- **Symlinks:** a symlink as a rename source is rejected, the temp file follows no symlink. **Backup folders** are never reused (even if the journal is missing). **Journal fields** with the wrong type and paths with invalid UTF-8 no longer throw an exception.
- **Rule download:** If the cross-check fails and there is no predecessor file, the new file is set aside instead of staying active; if the log entry fails, the old state is restored (otherwise there would be no rollback). The rollback protection also compares with the highest not yet rolled-back installation according to `update.log`, not only with the loaded version.
- **Not implemented:** journal rotation (it now grows linearly instead of quadratically) and a `realpath` comparison for folder symlinks below the roots (requires local write access).

## Addendum: database check (11 Nov 2026)

The system software stores apps, licenses, saves, downloads and notifications in SQLite databases (`/system_data/priv/mms/*.db`, `license/entitlement4.db`, `pbtc/pbtc.db`, `cache/httpcache/nobackup/cache.db`, `system_logger2/nobackup/database/*.db`, `savedata*/<uid>/db/user/savedata.db`). The collector `collect_databases` checks them in two stages, read-only (`db_version` 2026.11.21, 59 rules):

- **Stage 1, header and size** (read 100 bytes): SQLite signature, page size (power of two 512..65536), payload values 64/32/32 at bytes 21..23, page count in the header against the file size (applies only if the change counter at byte 24 equals "version-valid-for" at byte 92), file size a multiple of the page size, journal with the signature `d9 d5 05 f9 20 a1 63 d7` (open transaction). Source: sqlite.org/fileformat2.html. Rules: `db.header_invalid`, `db.truncated` (warning) and `db.journal_pending` (note).
- **Stage 2, content** (`libmedic/src/sqlite_check.cpp`, SQLite 3.54.1 from `third_party/sqlite3/`, public domain): `PRAGMA integrity_check` on a **copy in memory**. SQLite is compiled without file access (`SQLITE_OS_OTHER`), so it can open, change or delete nothing; the file is read twice, and if they differ (the console is writing at that moment) no check is made. A WAL with entries is included in the copy (valid, completed entries as with SQLite; a WAL with an invalid header is likewise ignored by SQLite). No check is made for a conspicuous header, an open rollback journal, a file or WAL over 32 MiB, and in case of a difference between the two reads. The reason is stored in the fact `integrity_skip` (`kopf`, `journal`, `gross`, `wal_gross`, `aendert_sich`, `klein`, `unlesbar`, `nicht_startbar`); "not checked" is a state of its own and never means "healthy". Rule: `db.integrity_failed` (warning). The SQLite message is stored as the fact `integrity_note`, not in the evidence (the snapshot export cannot reproduce it).
- **On the test console** (payload, 11 Nov): 15 files, all headers fine; 14 passed the `integrity_check` (also `cache.db` with its WAL), not checked is `sl2_log.db` (252 MB, `integrity_skip` = `gross`): the system logger writes to it continuously, a check would be slow and could produce false findings due to write operations. The databases are therefore healthy. The findings are checked against real databases only negatively; the positive cases are synthetic (fixtures `db1_*`, `db2_*`: real SQLite files with synthetic content, in one of them page 2 is destroyed).
- **Note text:** no update recommendation. It names Sony's Safe Mode item "Rebuild Database" with the reservation that the effect on titles mounted via ShadowMount+ is **not verified**, plus: first restart normally and check again, note installed titles, back up saves.
- **Origin of the idea:** structure of the check (SQLite without file system, database via `sqlite3_deserialize` from a copy, switch the copy's WAL mode to rollback) after PS5 Cleanup 1.0.7 (da_Chris86, GPL-3.0-or-later). The code is written independently; entry in `THIRD_PARTY.md`.
- **Deliberately open:** Very large, continuously written databases (`sl2_log.db`) remain unchecked. The behavior when the console is writing is secured only via the double-read probe, not verified on a deliberately damaged real database of the console (fixtures `db2_wal_*` use real SQLite files with WAL and SQLite itself as the touchstone).

## Addendum: file names in game folders, `game.il2cpp_case` (11 Nov 2026)

- **Case:** Unity games load `Media/Modules/Il2CppUserAssemblies.prx`. If `Il2cppUserAssemblies.prx` (lowercase "c") is there, the game crashes right after start on a file system that distinguishes upper and lower case (SIGSEGV in the `eboot.bin`, address 0x0). - **On the test console** (payload, 11 Nov): two Unity games on the USB drive (exFAT) carry the wrong spelling; `game.il2cpp_case_latent` reports them, `game.il2cpp_case` rightly stays silent. Fixtures `gc1_*` are synthetic.

After a successfully applied repair, the UI re-checks by itself (screen "Repair done"): first "Checking again …" is drawn, then the check-up runs once, and the display says whether the rule of the repaired finding is still reported (green: "… is no longer reported"; orange: "… is still reported. ## Addendum: confidence with reason (11 Nov 2026)

Every finding now says how certain it is and what the statement rests on (guiding rule 3 in `docs/en/DIAGNOSE.md`: keep evidence separate). This does not replace `verified` (status of the rule's source) but supplements it with the reliability of the finding on the console.

- **Fields:** `level` = `high` | `medium` | `low`; `basis` = `observed` (read or measured on the console, without any assumption about the cause), `doc` (documented), `community` (report from the community), `derived` (derived from observation or a report), `unknown` (not confirmed). The basis concerns the interpretation ("this is the cause"); that the file that was read really looks like that is always observed.
- **Rules file:** optional object `confidence` with `level`, `basis` and the mandatory field `reason` (`de`/`en`). Without an entry, the default derived from `verified` applies: `doc` = high/documented, `community` = medium/community, `todo` = low/not confirmed, without a reason. If one of the two fields is missing, it comes from the default; an entry always needs a reason.
- **Loader checks for contradictions:** `todo` never has `high`; `high` only with `doc` or `observed`; the basis must not be stronger than `verified` (`todo`: no `doc`/`community`, `community`: no `doc`). Like every text, the reason is subject to the text policy (no system update). A test enforces that every rule with `verified: todo` explains its reliability.
- **Rules with an explicit entry (18):** all twelve rules without a source (`todo`), the four database rules and the two game-folder rules (`game.il2cpp_case*`). Example `savedata.foreign_account`: medium, observed; the reason says that the differing account ID was read, but the connection with the "damaged data" message was observed only on the test console with three games and has not yet been confirmed by restoring the old account ID. `db_version` 2026.11.25.
- **Display:** detail view of the UI (top right "Confidence: medium (observed on the console)", green = high, orange = low, medium neutral; below it the reason, at most three lines, fewer if space is short), report (line "Confidence: … Reason: …" below the source), `medic-cli` (text and JSON `confidence`) and the diagnostic payload ("Verlaesslichkeit: level/basis"). The previous display of the source at the top right ("Source: documentation") is dropped in the UI, the source is still shown below it; the report keeps the source line.
- **Tests:** loader (default, partial entries, all rejected combinations, text policy), rules file (todo without a reason, todo with "high"), evaluation against `d2_pos` and `db2_pos_corrupt`, report (DE/EN), UI (colours, reason appears).

## Addendum: rule package governance (11 Nov 2026)

What already applied: The rollback protection ("not newer") compares a package not only with the loaded file but also with the highest not-yet-reverted installation in `update.log`; a download is valid only with a valid Ed25519 signature, and the key ID selects the key from the built-in list (so a second key can be introduced later without breaking old signatures).

New: **format level.** Rules and error-code files have the optional field `requires_level` (integer >= 1, 1 if omitted). The app knows one level (`kRuleFormatLevel` in `rules.hpp`, currently 1). A file with a higher level uses additions to the rule language that the app does not know; it is rejected with the identifier `needs_newer_app` ("needs a newer PS5 Medic version") instead of being evaluated wrongly or reported as "invalid". Anyone who extends the rule language (new operator, new mandatory field) raises the level in the app and sets it in the new file. Level 0, text or a decimal number are invalid.

Deliberately not built: an **expiry date** (`expires`). The console has no reliable clock for this purpose, a rules file used offline should not expire by itself, and the rollback protection already prevents installing older packages. A **second key** first needs a key change by Marc (the private key is never in the repository).

## Addendum: history of the check-ups, history and urgency per finding (11 Nov 2026)

Every check-up of the UI appends a line to `/data/ps5medic/history.jsonl`: time, rules version, firmware and the reported rules (only rule ID and severity; no paths, titles or identifiers of the console). The log belongs to the app, not to the user: at 256 KiB the file is moved to `history_<time>.jsonl` (never deleted, never truncated) and the new one starts with the most recent 50 checks. Broken lines are skipped when reading; without write access or a valid clock, only the comparison remains.

- **History per finding** (`status`, `first_seen`, `seen_runs`): "new since the last check" or "since <day> (n checks in a row)", compared with the last check; a gap ends the streak. Without an earlier check it stays empty (no comparison, nothing invented).
- **Resolved:** Rules that the last check still reported and that are now missing appear in the report as "Resolved since the last check (n)". The re-check after a repair runs through the same path and thus belongs to the history.
- **Urgency** (`high`/`medium`/`low`): critical = high, warning = medium, notice = low; from three checks in a row one level higher, unless the confidence is low. It only orders the display and never triggers a repair; the findings list stays sorted by severity.
- **Display:** detail view (small line below the header line), report (line "Urgency: … History: …" and the section "resolved"), `medic-cli` (JSON `urgency`; without history on the PC). The diagnostic payload writes no history.
- **Tests:** `tests/test_history.cpp` (comparison, gap, urgency, tolerant reading, appending, moving aside, report) and `test_ui.cpp` (service writes and compares, details distinguish new/recurring). Tests that check "nothing written" ignore `history.jsonl`.
- **Not yet:** baselines (measurements such as temperatures over time) and `pending` → `confirmed` for findings that should count as confirmed only after several checks.

## Addendum: measurements in the history and "provisional → confirmed" (11 Nov 2026)

- **Measurements (baselines):** `rules.json` has the optional list `metrics` (`id`, simple fact path `fact` without `[]`, `unit`, name `de`/`en`; schema in `rules.schema.json`). Five measurements: CPU and SoC temperature, free space on `/data` (new fact `storage.data_free_pct`), restarts without shutdown in 14 days, entries in the error history. Every check-up writes the values to `history.jsonl` (numbers only). The report has the section "Measurements": current value, value of the last check and the usual level (median of up to 20 earlier checks, shown only from three values). This makes a value like "70 °C, usual ≈ 45" interpretable without having to prescribe a threshold. The thresholds of the rules do not change as a result.
- **Provisional → confirmed:** A rule can require `confirm_runs` (1 to 10, default 1). Until the finding has been reported that many times in a row, it counts as provisional: it is shown, but marked as such in the details ("Provisional (1 of 2 checks in a row)") and in the report; a single measurement can be an outlier. Without history, the first check counts as one. First use: `sys.temp_high` (snapshot) with `confirm_runs: 2`. `db_version` 2026.11.26.
- **Tests:** loader (measurements, `confirm_runs`), measurement facts against `sys_pos_temp`, median and gaps, writing/reading, report DE/EN, display in the details.

## Addendum: reading the kernel log, D10 (11 Nov 2026, approved by Marc)

Marc approved D10 ("read klog"). It is read **through the kernel log server** (`klogsrv`, port 3232 on 127.0.0.1), not through `/dev/klog` itself: the device cannot be opened by two readers at once, and `klogsrv` keeps it open. Medic sends nothing and reads at most 256 KiB in 1.5 s (new platform function `ISystemInfo::read_local_stream`).

**Measured on the test console (read-only, 11 Nov 2026):** The server delivers **the backlog since the last reader and only new lines afterwards**: a first capture had 1535 lines (98 KB), the next two connections two lines each. **Reading therefore consumes** what has accumulated; another viewer (e.g. `nc host 3232`) will then no longer see those lines. Consequences for interpretation: the first check-up after startup sees everything since startup (as far as the buffer reaches, including messages from kstuff while hooking), later ones see only new lines; **"nothing in the kernel log" never means "all fine"**. The coverage list therefore carries the area "Kernel log (backlog since the last read)"; without a reachable server it is listed under "not checked".

**Privacy:** The log contains a lot (title names, identifiers, network addresses, the output of all payloads). Only lines with error words (`error`, `fail`, `panic`, `fatal`, `crash`, `assert`) or from kstuff or `[KERNEL]` (warning/error) are kept, without the priority prefix (`<118>`), truncated to 220 characters, without duplicates, at most 120; **output from payloads (`[payload.elf]`, including Medic itself) is skipped**, otherwise Medic would read its own output. The remaining lines are only counted (`klog.total_lines`). The report masks addresses and identifiers as usual.

**Facts:** `klog.readable`, `klog.total_lines`, `klog.lines[]`. The snapshot export writes the filtered lines to `klog.txt` in the snapshot folder; the fixtures replace the port with such a file (`k1_*`, synthetic).

**Rule `kstuff.shellui_patch_failed`** (struck on 13 Nov 2026 at Marc's decision; text kept as history) (hint, community, reliability low; originals read): The line `[kstuff.elf] … patch_shellui … failed` or `Failed to get libSceNpTrophy handle` shows that kstuff could not set the trophy hook in SceShellUI. According to kstuff-lite #95 (version 1.11, FW 13.42), the hook succeeds at startup and fails after switching between apps; #106 reports missing trophies. The author of #95 is unsure about the cause, no maintainer has replied; on this console (FW 12.00, kstuff-lite 1.10) the line was in the first capture (`Failed to get libSceNpTrophy handle, patch_shellui failed`); whether trophies are missing as a result has not been checked. `db_version` 2026.11.33.

**Not built (proposal D10b):** Because reading consumes, only the first reader sees the backlog. A later extension can collect the filtered lines per console boot in a file of its own under `/data/ps5medic/` (append lines, start anew at a new console boot, never delete) so that later check-ups see them too. This would additionally write and is still awaiting a decision.

### Supplement: collecting the kernel log per console boot, D10b (11 Nov 2026)

Because reading from `klogsrv` consumes, the UI appends the newly read, filtered lines to `/data/ps5medic/klog_boot.txt` at every check-up (`persist_klog` in the service, after collecting and before evaluation) and reads them back in at the next check-up. This way a later check-up also sees what was reported at startup or in between.

- **Format:** first line `# boot <console start time>`, then one line per entry (the same filtered, truncated lines as in the fact, without duplicates, at most 256 KiB). Without a known start time, nothing is written.
- **New console boot:** The old file is **moved** to `klog_boot_<old start time>.txt` (never deleted, never overwritten; if the move fails, everything is left untouched) and a new one is begun. A foreign file of the same name (without a header line) is not touched. The old files accumulate (at most 256 KiB each); cleaning up is up to the user.
- **Facts:** `klog.new_lines[]` (only what was read in this check), `klog.persisted_lines` (number of lines from earlier checks of the same boot), `klog.lines[]` (both together, at most 200, the new ones last). Lines from an earlier console boot do not count.
- **Limits:** Collection only happens at UI check-ups (the diagnostic payload is read-only and does not collect). Anything another reader consumed before Medic is still missing. The file may contain title names and paths from error lines (same filters as the fact), but lies only in Medic's own folder; the report masks as usual. Fixtures `k2_*`, tests (append, duplicates, later check-ups, restart moves, write protection, foreign file).

## Addendum: local network test `sw.net.local` (11 Nov 2026, approved by Marc: local only)

Exception to D1 and to guideline 5: The self-test (standard tier, also runs in the diagnostic payload) measures the connection between the console and the router.

- **Gateway:** `ISystemInfo::default_gateway()` reads the default route from the routing table (PS5: `sysctl NET_RT_DUMP`; snapshot: `gateway` in `system.json`). Fact `net.gateway`. The test addresses **only** addresses in the private range (10/8, 172.16/12, 192.168/16, 169.254/16); everything else is `skipped` with `not_local`, nothing is sent.
- **Measurement:** `ISystemInfo::tcp_probe()` only establishes a TCP connection (non-blocking, deadline 1 s) and closes it again; **no data** is sent. "Connected" and "refused" (RST from a port without a service) count as a response. First, ports 80, 443, 53, 22 of the router are tried in turn until one responds; then 20 attempts on that port with a 150 ms pause (at most about 25 s).
- **Status:** if the router responds on no port (many silently drop), the test is `skipped` (`no_response`): silence is no statement about the network. No gateway: `no_gateway`; send error: `probe_error`. **Never `failed`.** `warn` at a loss of 20 % or more (`packet_loss`) or a mean response time above 100 ms (`slow_gateway`); both thresholds are our own assumptions. Measured values `probes`, `loss_pct`, `rtt_avg_ms`, `rtt_max_ms`.
- **Rule `selftest.net_local`** (hint, todo, reliability low): explains both warnings (Wi-Fi reception, cable, restart the router). Only the path to the router is measured, not the internet; no statement about download speed. `db_version` 2026.11.35.
- **Does not prove:** internet, speed, Wi-Fi signal strength, other devices on the network.
- Tests: snapshot probe via `system.json` (`net_probe`: `reply`, `rtt_ms`, `loss_every`), fixtures `n1_*`.

**On the test console** (FW 12.00, diagnostic payload): gateway found in the routing table, `sw.net.local` **passed** (20 attempts, 0 % loss, mean response time 5.5 ms, maximum 47 ms).

## Addendum: reading eboot.bin from game images (12 Nov 2026)

`libmedic/src/imgread.c` is a small, **read-only** reader for game images, taken over from PS5 Cooling & System Center (same author, GPL-3.0-or-later): `.exfat` (exFAT), `.ffpkg` (UFS2) as well as `.ffpfs` and `.ffpfsc` (PFS containers holding an exFAT image, uncompressed or PFSC-compressed respectively; the blocks are inflated by libdeflate, `third_party/libdeflate`). It recognizes the format from the first blocks, not from the name. `libmedic/src/image_reader.cpp` attaches it via `IFileSystem::read_range`, so that the core also runs on a PC against fixtures. The images are not mounted and nothing is modified.

With this, `collect_game_firmware` reads the SDK version of the `eboot.bin` (two small read accesses) also for games that exist as an image. **Confirmed on the test console:** All 14 images (`.exfat`, `.ffpfsc`, `.ffpkg`) could be opened and their `eboot.bin` read (header `4F 15 3D 1D` or `54 14 F5 EE`); an image game (`param.json` requires 13.60) is no longer reported as "needs backport", the backport is inside the game; a game as a folder had been recognized before. Other formats and damaged images are not read (the finding then remains). Fixtures `g1_neg_inline_image`, `g1_pos_image_ebootnew`, `g1_neg_inline_ffpfs`, `g1_neg_inline_ffpfsc` are generated by `tools/gen_exfat_fixture.py` (the `eboot.bin` lies fragmented in the FAT chain; the test covers exFAT, PFS and PFSC, UFS2 was only checked on real images of the test console). For such games the snapshot export creates a tiny exFAT substitute image with the substitute `eboot.bin` (`build_exfat_stub`, `libmedic/src/exfat.cpp`); the reader recognizes the format from the content, so this also works under the name `.ffpkg` or `.ffpfsc`.

**Thermal test aborted with `stalled`, cause and correction (14 Nov 2026, consoles .52 and .94).** The test ended after about 3.4 s with `cancelled` / `stalled`, on both consoles (the heartbeat guard had noticed the stalled service). New diagnostic measured values in the result (without influence on the verdict): `cpus_online` (`sysconf`), `threads_started`, `steps`, `max_step_gap_ms`, `rounds_min_thread`, `rounds_max_thread`. The run on .52 showed: `cpus_online` 16, 8 compute threads, the service got to run only **2 times** in 3.8 s (`max_step_gap_ms` 3776), the threads ran very unevenly (1 versus 35603 rounds). The console apparently does not time-slice threads of the same priority; the compute threads occupy the usable cores, the main thread waits. `sysconf` reports more cores than a process may use, which is why "leave two cores free" did not help. **Correction:** Each compute thread calls `sched_yield()` after every round (about 0.1 ms) (the only new import, from `libkernel`). Result on .52 afterwards: `passed` (reason `fan_controller`, rise 49 → 52 °C), `steps` 901, `max_step_gap_ms` 46, rounds per thread 60253 to 60320 (even), throughput first versus last 10 intervals −0.9 % (no throttling), 0 compute errors, duration 30.4 s. Thresholds and evaluation of the test are unchanged.

**Fan controller text kept general (Marc, 14 Nov 2026).** There are several apps that control fan regulation, not only the PS5 Cooling Center. The reason `fan_controller` of the thermal test therefore reads in all languages "Fan controlled by an app: keeps the console cool (weak statement)" and names no app; likewise the "Does not prove" text of the test. Still only the Cooling Center is detected (via its `config.json`); other apps remain invisible (all payloads are named `payload.elf`), in which case the test can only report `no_heating`.
