# The UI as a native app (status 12 Nov 2026)

[Deutsch](../NATIVE.md) · **English**

**Why:** So far the UI has run as the borrowed Big App `FAKE00000` (the loader from websrv puts it into the shell of the PSNow app). In that shell the PS button does not lead to the home screen (only a sound, see `docs/en/AUDIT.md`). A native app with its own title behaves like any other app.

## Design
Two parts, because a sandboxed app may not read `/mnt` and the system folders:
1. **UI app** (`ps5/native_ui_main.cpp`, own title, folder app in `/data/homebrew`): display only. Image via VideoOut (tiled frame memory), pad via ScePad, without SDL and without privilege elevation. It keeps the service's images in a buffer and sends the pad state back.
2. **Service payload** (`ps5/service_main.cpp`, `make ps5-service`, `ps5medicservice.elf`): runs through the ELF loader with full privileges, draws the **entire UI** (the same `App` + `LocalService` as the SDL UI, so checks, repairs, undo and rule update are unchanged) and sends only the changed image strips (8 scanlines) to `127.0.0.1:9060`.

Protocol: `ps5/service_protocol.hpp` (type, length, payload; `H` hello, `B` strip, `P` frame done, `Q` end; app -> service `S` pad state, `X` quit). The app starts the service itself when needed: it reads `/data/homebrew/PS5MEDIC/ps5medicservice.elf` and sends it to port 9021. The service ends with the UI (Circle on the start screen), after 120 s without an app, or on `X` from a newer instance.

Decision (12 Nov 2026): Instead of transferring every `IMedicService` call (more than 30, many structures), only image and input are transferred. This saves most of the work and keeps the logic in one place. The SDL UI (`ps5medicui.elf`) and `LocalService` remain as a fallback.

## Build
`make native-ui` (script `title/build_native_ui.sh`) builds `build-native/FAKE42007/`, `make deploy-native PS5_HOST=<ip>` puts it into `/data/homebrew/FAKE42007` via FTP (ShadowMount+ creates the "PS5 Medic" tile; with `NATIVE_ID=FAKE42009` a test tile is created next to it). Basis: `ps5-native-tool`, `libc.prx` and the small C++ runtime from ps5-native-app-boilerplate, SDK 0.45.

Constraints of the environment that shape the code:
- **No exceptions, no RTTI.** The core stays built with exceptions; for the app, the parts it needs were split out (`libmedic/src/finding.cpp`: `to_string(Severity/TestStatus)`, `effective_confidence`, `urgency_of`) and the rest is pure UI (`ui/src/*` without `png.cpp`, `local_service.cpp`, `shot_hook.cpp`), plus `diff.cpp`, `qr.cpp`, `checks.cpp`.
- **No iostream, no unwinder.** `qrcodegen` is included via `ps5/native_qrcodegen.cpp` without `ostringstream` and with `throw` = abort; `ps5/native_shim.cpp` replaces the `_Unwind_*` entry points of libc++abi.
- `libc++.a` and `libc++abi.a` of the SDK are linked statically (for `std::string` etc.).

## Status
- **Milestone 1 (confirmed on the console on 12 Nov 2026, FW 12.00):** image, pad and **the PS button leads to the home screen** (in the borrowed Big App `FAKE00000` it did not work). Findings during the test: (1) the app heap is small, so large blocks go through their own memory pages (`ps5/native_runtime.cpp`); (2) the frame memory is tiled (`ps5/native_tilemap.inc`, from the SDL driver); (3) when quitting with the PS button, the app keeps running in the background and its files stay locked until it is closed (FTP 550). Original plan: UI with a placeholder service (`StubService`, reports "Check incomplete"): image, pad, splash screen, background. What was checked: does the app start, does it show the image, does the pad respond, **does the PS button lead to the home screen**, does Circle quit the app.
- **Milestone 2 (12 Nov 2026, UI appears on the console):** service payload and display app run; the app starts the service itself. Open: confirm pad control and the check-up with real findings.
- **Startup time (12 Nov 2026, measured):** from the start of the app to the first image 2.2 s, with the splash screen's bar tracking the service's loading progress. Gained by: text policy with a pre-check instead of 12 regex searches per text (rules 2.1 s -> 21 ms, error codes 1.4 s -> 7 ms) and background construction without `hypot`. Remainder: the first drawing of the UI (~1.5 s).
- **Milestone 3 (12 Nov 2026, after the check-up test):** The native app is now the tile `FAKE42007` "PS5 Medic" (`make deploy-native` builds it and puts it, together with `ps5medicservice.elf`, into `/data/homebrew`). `make dist` packs tile and service instead of starter, launcher and SDL UI. The launcher for sending (`make send-launcher`, see below) now creates tile and service itself.

## Installer for sending (`make send-launcher`)
Without FTP: `make send-launcher PS5_HOST=<ip>` sends `ps5medic-launcher.elf` (`ps5/installer_main.cpp`, around 11 MB) to the ELF loader (port 9021); `make dist` puts it as a separate file `dist/ps5medic-launcher.elf` next to the zip (it is not inside the zip; on GitHub it is attached as a separate release file next to the zip). The ELF carries all files of both folders and writes them to `/data/homebrew/FAKE42007` (`eboot.bin`, `sce_module/libc.prx`, `sce_sys/icon0.png`, `sce_sys/param.json` last) and `/data/homebrew/PS5MEDIC` (`ps5medicservice.elf`, `rules.json`, `error_codes.json`, `sce_sys/icon0.png`). ShadowMount+ then creates the tile; the installer starts nothing and needs no elevated privileges.
- Each file is first written as `<name>.new` and then renamed, so a running app or service never sees a half-written file. Files that are already identical are left untouched; nothing is deleted.
- The files get mode 0777 as with FTP uploads. Without it (only 0666) the app did not start: ShadowMount+ started it, it ended after about one second without an entry in `native.log` (console, 13 Nov 2026, found in the ShadowMount+ `debug.log`: start and release one second apart).
- New imports of the app: `title/build_native_ui.sh` compares the imports with `title/native_imports.txt` and aborts on new ones (e.g. `fgets` was presumably missing in the runtime; not finally clarified, but the app may only import known things).
- Log: `/data/ps5medic/installer.log`, plus a message on screen. `make send-launcher` first rebuilds the app (`make native-ui`) and the service so that the ELF carries the current state.
- Console test 12 Nov 2026 (FW 12.00): sent twice to an already installed tile; `eboot.bin`, service, icons and `param.json` were recognized as already current, `rules.json` and `error_codes.json` were rewritten (renaming works). Empty installation checked on the console on 13 Nov 2026 (test build with `make ps5-launcher INSTALL_ROOT=/data/ps5medic/install_test`, which writes into an empty test folder): all eight files created including subfolders, no `.new` leftovers; the test folder was removed afterwards.

## Open risks
- Review of 13 Nov 2026, second round (fixed the same day): the pad direction is reset when the pad is lost (the app sends the idle state once); an invalid strip 'B' under 4 bytes is skipped; the message "Connection to the service lost" stays for 2.5 s and in all error screens Circle quits the app; the app's language detection reads `config.ini` like the UI (whitespace around `=`, comment lines, last line wins, up to 4095 bytes); `reload_rules`/`reload_error_codes` take the file with the higher `db_version` (`knowledge/` or bundled); self-test: without a writable marker the load and write tests do not run, a result that was not saved is reported, an exFAT image without a readable header counts as a finding; the game detail truncates extra lines so that nothing runs over the panel. Since the overall review of 13 Nov 2026 (`docs/en/AUDIT.md`), a pad that returns only read errors for 5 s (or reports "not connected" for 30 s) is closed with `scePadClose` and reopened; the import `scePadClose` is in `title/native_imports.txt`, and the app starts with it on the console (FW 12.00, 13 Nov 2026, `native.log`: "Pad geoeffnet", first image, clean quit with Circle). The reopen path itself (read errors over 5 s) was not triggered in that test and has only been checked in the PC code. The idle state is only sent while the connection to the service is up.
- Review of 13 Nov 2026 (deliberately not changed): The service serves one app at a time; a new service cannot replace a running one as long as the app is connected (`Address already in use`, an update only takes effect after quitting the app). Port 9060 on 127.0.0.1 is unauthenticated: any local process could send pad inputs or quit the service (local only, every repair requires several inputs, backup and undo).
- The app's imports (libc, `libScePad`, `libSceVideoOut`, `libSceUserService`) are confirmed on FW 12.00; unchecked on other firmwares, a missing import ends the app before `main()` without a message.
- The app can create, write and read files under `/data/ps5medic/` (confirmed: `native.log`). Listing folders and `stat` are denied from the sandbox according to the boilerplate docs, `/mnt` and the system folders stay inaccessible: the service payload remains necessary.
- Lapy sandbox elevation (from the boilerplate) would be a way to save the service; it is only confirmed on FW 6.02 to 12.70 and is deliberately not used.
- Controls (13 Nov 2026, Marc: "a bit slow"): The service slept a fixed 33 ms per pass, so each key waited 16 ms on average, 33 ms at most. Now the app's input (`poll`) wakes it, it draws immediately after a key and otherwise every 16 ms; `App::update()` keeps running about 30 times per second (splash screen, dots, self-test steps depend on it). When idle, the app polls every 3 instead of 8 ms. Repeat of held directions: 300 ms, then every 70 ms. Not measured on the console; the PC draws a frame in 3 to 8 ms.
- Review round of 14 Nov 2026 (service and app): After a long operation (over 250 ms: check-up, download, self-test step), the service discards the pad states accumulated in the meantime and reads the next one only as a new baseline; otherwise a queued Cross on the following screen triggered an action. `service.log` is only rotated once the port is bound (a second instance only appends its lines). Exceptions in `serve()` end only the session. The app switches to the error screen after 60 s without a first image (Circle quits it). The heat test stops its compute threads if the main thread has not advanced for more than 3 s.

## Version matching of app and service (16 Nov 2026)

- **Occasion:** After an update, an older service stayed in memory on the .94 (the app had not been left via "Quit"). The new app connected to it instead of sending the new one; the check-up ran with old code (12 instead of 26 facts, no `setup`).
- **Procedure:** The service appends its **build ID** to the hello (`'H'`: u16 width, u16 height, then ASCII; an older service sends only 4 bytes). The app compares it with its own. If it differs or is missing, the app sends `'X'` (quit), waits up to four seconds for the port to become free, and sends the new service as usual. **At most once per app start**: if the IDs never become equal, it stays at one attempt, after which the running service is accepted.
- **ID:** `tools/build_id.sh` hashes the source files (`libmedic`, `ps5`, `ui/src`, `ui/include`, `ui/i18n`, `knowledge`); the Makefile (`-DMEDIC_BUILD_ID` for `service_main.o`) and `title/build_native_ui.sh` use the same script, `git` is not needed (the worktree directory is not readable in WSL). Without a value, `dev` applies (host build).
- **Consequence:** A change to sources or rules ends the old service once at the next app start and loads the new one. `native.log` then contains "Dienst hat eine andere Fassung (…) als die App (…): beende ihn und starte den neuen".

## ShadowMount+ must be running for the app to see its files (16 Nov 2026)

- ShadowMount+ places `/data` into the app's sandbox via FakeLib (in the log: "directory unmounted: /data -> /mnt/sandbox/FAKE42007_000/data"). While it is stopped, the app can neither write `/data/ps5medic/native.log` nor read `/data/homebrew/PS5MEDIC/ps5medicservice.elf`; the file is there via FTP, yet the app reported "Dienstdatei fehlt".
- The message is now "Service file not readable: …" and names ShadowMount+ in the second line: start it, wait briefly, restart the app (five languages, `ps5/native_ui_main.cpp`).

## Firmware matching of the imports (16 Nov 2026)

- **Question:** Do the service (179 imports) and the native app (92 imports) find all the functions they import on every supported firmware? `tools/fw_compat.py` computes the NID of each imported function (SHA-1 with Sony salt, checked against `sceKernelUsleep` and `scePadReadState`) and looks for it in the exports of the system libraries of each firmware (`libkernel`, `libkernel_sys`, `libkernel_web`, `libSceSystemService`, `libSceLibcInternal`, `libSceNet`, `libScePad`, `libSceUserService`, `libSceVideoOut`). The yardstick is 12.00, where the app runs; anything that does not come from the libraries there (loader, compiler runtime) does not count.
- **Required** (not in the repository, read only): a folder with decrypted system libraries per firmware (`<root>/<XX.XX>/…`) and the parser `build_import_export_db.py` (`--parser`). Invocation and options: head of `tools/fw_compat.py`; return code 0 = everything present, 1 = something missing, 2 = input error. Test: `tests/test_fw_compat.py` (in `make test`).
- **Result of 16 Nov 2026** (collection 1.00 to 12.70, 44 firmwares): All 179 and all 92 imports are present in **every readable firmware from 1.00 to 12.70**, i.e. in the whole supported range 4.00 to 12.70. At **7.00** the libraries are not readable (presumably not decrypted), which is unchecked.
- **Not covered:** Firmware **13.xx to 14.10** (the collection ends at 12.70): the statement "runs on 4.00 to 14.10" in the README is not backed up for these, only up to 12.70. Once these firmwares are placed in the folder, the run is a single command. Only the presence of the functions is checked, not their behavior and not the file paths that Medic reads.
